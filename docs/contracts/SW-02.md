# SW-02: Beacon contamination mask

Status: PROPOSED

| Field | Value |
|---|---|
| Objective | The node's own buzzer or LED cannot look like an event. Hazards are never masked |
| Owner / builder | B / builder agent |
| Branch | `codex/SW-02` |
| Depends on | SW-04 merged (merge-order reason only) |
| Stage order | Build, authorized verify, stage review, stronger (Opus) review, gate and human commit |
| Budget | 2 hours, 4 verifier attempts, no downloads, no paid API |
| Stronger review required? | **Yes**: new payload field and a path near hazard logic |

## Scope
1. `node_bridge.BeaconMask(beacon_s, guard_s, clock)` with `on_beacon()` and `overlaps(t0, t1)`. Config values: `BEACON_S = 2.0` (must equal the firmware's 2000 ms), `BEACON_GUARD_S = 0.3` (a bench value).
2. `node_bridge.build_message(node_id, node, feat, ts, masked=False)` adds `beacon_masked: true` **only when masked**.
3. The beacon command handler calls `on_beacon()`. Windows that overlap are marked. `--log` does not write masked windows to the normal CSV.
4. `Brain.on_node`: if `beacon_masked`, skip learned detection. Flame and water rules still apply.
5. Document the additive field in `bus.py`.

## Explicit exclusions
No firmware change. No dropping windows. No touching hazard rules. No firmware `bz` flag: the bridge knows when it sent the command.
